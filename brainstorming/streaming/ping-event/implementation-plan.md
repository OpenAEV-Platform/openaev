# 2. Implementation choice: one lot per entity

## Why per entity, not per screen

A lot moves **one entity's whole feature**: list, details page, creation, update, deletion, popovers, drawers
and bulk actions, with its stream type mapping and its tests.

- **One source per entity on a screen.** A details page on a query whose edit drawer still reads Redux shows two
  versions of the same entity after a change: the query refetches, the store waits for the stream.
- **The backend can only stop sending a type's content when no screen reads it.** Redux screens read the
  `instance` of the event. Splitting by screen leaves the type half read from the payload, so the security
  benefit (#8563: no content in the stream) never comes for that type.
- **The review and the tests match a feature.** One e2e spec per entity (list and details, two actors), one unit
  test per list, one manual marking check when the entity is marked.
- **A regression is bounded to one menu entry**, and a lot can be reverted alone.

Screens of *other* features that read the entity's store (an inject form listing endpoints) are listed in the
lot as "out of feature". They move with their own feature; until then the stream keeps feeding the store entry.
The type's content is removed from the stream only when that list is empty.

## Lot 1: every asset type at once

Endpoints, security platforms and AI targets ship together, with the agents shown on them.

- **One table, one id space**: `assets` (`@Inheritance(SINGLE_TABLE)`). The live layer already sees one type
  (`TYPE_OF` maps `endpoints`, `securityplatforms` and `aitargets` to `assets`). The inventory list, the asset
  details page and the asset popover already serve endpoints (every category) and AI targets.
- **One marking column**: the three subtypes are marked through the same `marking_ids` column of `assets`.
  #8563 is done for assets only when none of the three sends content any more; shipping endpoints alone keeps
  security platforms and AI targets leaking.
- **Agents are children of endpoints**: their change updates the asset (`PARENTS_OF`), and the 30 s throttle of
  the assets list exists because of their heartbeats. Their screens move with the assets.
- **Asset groups are not in lot 1**: another table, membership computed from asset filters (dynamic groups). They
  are the next lot: their queries `watch` assets.

What lot 1 still has to do (detail in 3.1):

1. The endpoint update drawer and the AI target drawer read the details query (today Redux and a one-shot
   fetch: the page and its drawer show two versions).
2. Security platforms: list, card grid, details page, creation, popover. Their list declares
   `collections: [assets]`, so it also refetches on every endpoint create or delete: accept it or give security
   platforms their own type.
3. The pickers (`EndpointsPicker`, AI target autocomplete) read queries, but keep writing their selection into
   Redux until the inject forms migrate (lot 4).
4. The CSV import describes its change instead of reloading the page.
5. Out of feature, kept on Redux: the inject forms' endpoint list, the simulation validation and timeline readers,
   the security platform logos of atomic testing results, `Scenario.tsx` agent health.

## Paginated lists: a fix, streamed or not

`PaginationComponentV2` fetches one page into local state, and 34 files then patch that state by hand after
their own mutations (`setContent`, `incrementTotalElements`, `handleChangeTotalElements`). The page drifts from
what the server would return:

- **Create**: the new row is prepended to the page, so a page of 20 shows 21 rows, whatever the sort and the
  filters (a row that does not match the filter, or sorts to page 3, still shows on top).
- **Delete**: the page shows 19 rows; the first row of the next page does not move up. A bulk delete leaves the
  page short by the number of rows deleted.
- **Update**: the row is replaced in place, even when the change moves it out of the filter or to another page.

`usePaginatedQuery` refetches the page after a change (`useLiveMutation` or `useApplyChanges`), so the page and the
total are always what the server returns. This holds for a type the stream never sends: its list query still
declares `liveMeta({ collections: [type], refs })`, so the user's own mutations refetch it; only other users'
changes wait for TanStack's defaults (mount, focus, reconnect). Credentials (`Credentials.tsx`) are the typical
case: not streamed by design, but their list has all three drifts.

So the migration to `usePaginatedQuery` is worth doing for every list, live or not. A list of a streamed type
moves with its lot; a list of a type not streamed can move at any time.

## Backend steps per lot

| Step | Backend | Frontend |
|---|---|---|
| **0. Prerequisites** | fix #9717 (duplicate events); cache `isFiltering()` | merge #8737 and #8916 |
| **1. Screens migrated** | — | the lot's feature reads live queries only (section 3) |
| **2. Out-of-feature readers gone** | — | each reader listed in section 3 is migrated, or reads a query of the lot |
| **3. Signal only for the type** | the type sends `instance: {<id>}` plus the signal marker (allowlist of types) | the Redux adapter does not store a partial entity for an allowlisted type |
| **4. Payload stripping deleted** | once injects, asset groups and findings send signals: user trimming, notifier redaction and the field-by-field filtering go | — |

Two types break completely without the payload and must be handled in their lot: `agents` (`Scenario.tsx` reads
`agent_asset` and `agent_active` from the stream only) and `notifications` (`TopBarNotifications` uses it as a
trigger). The Redux store deep-merges each event (`Referential.ts`): an id-only update would keep stale fields,
and an id-only create would add an empty entity, hence step 3's guard in the adapter.

Besides the Redux screens, one direct subscriber reads the payload: `NewsFeedToastManager` renders its toasts
from `instance`. The others (`useNewsFeedUnreadCount`, `useNewsFeedStreamRefresh`, `useAttackPathLiveGraph`)
only refetch or use their own named event.

A generic fallback in the Redux adapter (on a signal, re-run the mounted loaders of that type, throttled) would
let step 3 come before step 2 and decouple the backend cleanup from the out-of-feature readers. Whether to build
it is an open question of the technical design ("Redux fallback").

### Load during a running simulation

`injects`, `injectexpectations` and their results, `findings`, `communications` and the agent heartbeats change
continuously. Lots 3 and 4 decide:

- `refs` plus a `throttleMs` of several seconds on the timeline, overview results, Validations and charts; an
  aggregate (a count by status) uses `watch` with an even higher throttle; a list never uses `watch` on its own
  type.
- the store-driven `useEffect`s that refetch on every change (simulation healthchecks and drift, scenario
  healthchecks, target results) do not become per-event refetches.
- `collections: [injects]` on the atomic testing list refetches on every inject created anywhere, simulations
  included: filter by context in the key and accept it, or give atomic testings their own type.
- the polling to remove once live: atomic testing page (5 s), report generation. To keep until a signal exists:
  Logic and Scope (3 s), the attack path safety net.

### Notes

- **Store name ≠ stream schema for asset groups**: stream `assetgroups`, store `asset_groups` (`actions/asset_groups/assetgroup-schema.ts`). Every Redux reader of asset groups (detail page, manage drawer, `AssetGroupsList`, ToolBar, TeamOrAssetLine, ChainedTimeline, chaining scope) is not live today; stream events pile up in an unread `assetgroups` bucket. The live layer already uses `ENTITY_TYPES.ASSET_GROUPS = 'assetgroups'`, so a migrated query is fine.
- **Asset subtypes in three Redux buckets, one id space for queries**: endpoints → `endpoints`, AI targets → `aitargets` (not in `entitiesInitializer`), security platforms → `securityplatforms`; `TYPE_OF` maps all three to `assets`. Consequence: a security-platform list declaring `collections: [assets]` is refetched by every endpoint create/delete, and the inventory list by every security platform create/delete (filtered out server-side, so a wasted refetch). Consider a separate type or accept it.
- **Generic asset categories** (cloud, identity, web…) are `Endpoint` rows (created through `/api/endpoints/agentless`), so they stream as `endpoints`. Only `Endpoint` and `SecurityPlatform` extend `Asset`; base `Asset` rows are AI targets (stream `aitargets`) — a base Asset with another category would stream as `assets` (to check whether any exist).
- **Shared components used by several entities / features**: `AssetPopover` (inventory, asset detail, asset group management, inject forms), `EndpointUpdate` (from AssetPopover), `AssetsList` (asset group drawer, inject form), `EndpointsPicker` (asset groups, inject forms), `AssetGroupPopover` (asset groups, inject form, tag rules), `CredentialPopover`/`CredentialsList` (credentials, inject form). Their callers outside the feature pass entities from local state or Redux, so after the migration those callers still need prop-driven behaviour (or keep `onUpdate`/`useApplyChanges`).
- **Pickers write into Redux on submit** (`EndpointsPicker`, `AssetGroupsPicker`, `CredentialsPicker` dispatch `DATA_FETCH_SUCCESS`) so that the inject form lists (`InjectEndpointsList`, `AssetGroupsList`, `InjectCredentialReferencesList`) can render names. Removing these writes during the assets migration breaks the inject forms: keep them until the inject feature migrates, or have the inject lists fetch by id.
- **Mixed today on migrated screens**: the list and detail are 🟢, but the endpoint update drawer still reads Redux (`EndpointUpdate`) and the AI target drawer a one-shot fetch — the two-sources pitfall the skill warns about. Both drawers must move to `assetQueries.detail` (or a dedicated AI target query) in the same PR.
- **Lost update in asset group membership**: `AssetGroupManagement`/`AssetGroupPopover`/`AssetPopover` send the full `asset_group_assets` list computed from a Redux/prop copy that is never refreshed by the stream → a concurrent change by another user is overwritten. The migration fixes it only if the id list comes from a fresh query.
- **Dynamic group membership** changes when an endpoint changes, with no `assetgroups` event: group member lists/counts need `watch: [assets]` (throttled) or accept staleness until the next refetch.
- **Agents store** is fed only by the stream (no REST loader uses `arrayOfAgents`): `Scenario.tsx` sees an agent only after its first event since page load.
- **Markings**: only assets (endpoints, AI targets, security platforms) are marked. With `MARKING` on, a marking change streams as a delete/create to each reader (commit f586d57ff8) and a clearance change triggers a re-read (c00a62cd5f); asset groups and credentials are unmarked, but group member lists are filtered by the members' markings.

### Notes

- **Counts (rows, out-of-feature rows included):** 🟢 0 · ✅ 36 · ⚠️ 33 · ⛔ 21 · 🔵 3 · n/a 4 (writers, placeholder, no admin screen) · 5 pointer rows (status given in other rows).
- **Store-name / type mismatches:**
  - `inject_statuses` (Redux) vs no stream at all: `InjectStatus` has no listener; its transitions reach screens only as an `injects` update carrying `inject_status`. A live query on statuses must use `refs` on the inject.
  - `workflowconfigurations` is a client-only key with no backend entity; scope rules and variables stream as `workflowscoperules` / `scopevariables`; steps and workflows are not streamed. Chaining screens rely on 3 s polling.
  - `InjectExpectationResult` streams as `injectexpectationresults` with its own id under `attribute_id` `inject_expectation_id`: a naive mapping would mistake a result id for an expectation id. Map it to its expectation, or rely on the parent expectation's score update (to check).
  - `findings` and `reportings` / `reportinggenerations` are written to dynamic Redux buckets nobody reads.
  - `atomics`, `atomicdetails`, `targetresults` are dead stores (no writer, no reader): delete them in the atomic testing migration.
  - Atomic testings are `injects`: one `INJECTS` type serves the atomic testing list, the simulation inject lists and the cockpit. Queries must filter by context in their keys, and a list `collections: [INJECTS]` refetches on every inject created anywhere (including every simulation's injects).
- **Not streamed, so never live without polling or a new signal:** execution traces, inject tests, finding occurrences, steps / workflows, imported injects (`setListened(false)`), anything inside a bulk operation.
- **Shared components across entities:** `InjectResultList` (atomic list + simulation overview), `AtomicTestingRoutes` and all `atomic_testing/*` tabs (atomic page + simulation inject page, with two different `updateInjectResultOverviewOutput` contracts: refetch vs set), `FindingList` (4 contexts), `ExecutionOverview` (simulation + scenario execution tab), `Injects.tsx` / `ChainedTimeline` / `InjectPopover` / `UpdateInject` (simulation + scenario), `ExercisePopover` + `SimulationList` (simulations list + scenario overview), `EntityReportsPanel` (7 detail pages), `useSimulationPermissions` (every simulation screen).
- **High-frequency types during a running simulation:** `injects` (each status transition: QUEUING → EXECUTING → PENDING → terminal, per inject), `injectexpectations` and `injectexpectationresults` (per target × agent × expectation type, from collectors and agents), `findings` (bursts at output parsing), `communications` (one per player per mail), plus `agents` heartbeats on asset chips. Risks:
  - Today `useDataLoader` re-runs every mounted loader on reconnection and bulk end: on the cockpit that is a full reload of all injects and all expectations of the simulation.
  - Store-driven `useEffect`s refetch on every store change: simulation healthchecks and drift (on the exercise object), scenario healthchecks (on `scenario`, `injects`, active agents), target results (on the overview object). A migration must not turn these into per-event refetches.
  - Cockpit, overview results, validations and charts need `refs` + a raised `throttleMs` (several seconds), aggregates `watch` with an even higher throttle, never `watch` on a list's own type.
  - The Redux LRU cap of 5000 entries on `injects` / `injectexpectations` can already truncate what the cockpit and Validations show on large simulations (to check).
- **Polling to remove once live:** atomic testing page (5 s), report generation (page, tab, `EntityReportsPanel`). Polling to keep until a stream signal exists: Logic (3 s), Scope (3 s), attack path delta safety net.
- **Pre-existing bugs found:** `MailDistributionByInject` reads `getScenarioInjects(exerciseId)` (filters on `inject_scenario`), so it is always empty for a simulation; the simulation inject result page (`InjectIndex`) never refreshes while the simulation runs (no poll, no store).
- **Marking:** only `Asset` is a `MarkedEntity`; injects, expectations, findings and traces are marked through their target asset. Test with the `MARKING` flag and a restricted reader on the cockpit, Validations, target results, traces and findings.

### Notes

1. **No 🟢 screen in this domain.** `ENTITY_TYPES` needs new entries before any migration: `teams`, `users`, `organizations`, `documents`, `channels`, `challenges`, `lessonstemplates`, `lessonstemplatecategorys`, `lessonstemplatequestions`, `phishinglandingpages`, `phishingemailtemplates`, `customdashboards`, `widgets`, `notifications`, `notificationtriggers`, `newsfeeditems`. Every one of these equals its Redux store key except the ones with no store.
2. **Store name ≠ stream schema:**
   - `injector_contracts` (store) vs `injectorcontracts` (stream). `InjectorContract` has an `@EmbeddedId`, so the schema is the simple class name. No contract update ever reaches Redux.
   - Custom dashboards, widgets, triggers, notifiers and news feed items have **no store key**: their events are merged into keys nobody reads. Deletes are dropped, because `DATA_DELETE_SUCCESS` ignores a missing key.
   - `CustomDashboardParameters` streams as `customdashboardparameterses` (class name ends with "s").
3. **Admin-only events (resource type UNKNOWN):** articles, variables, the three lessons template types, widgets, challenge flags and dashboard parameters. A live query on them stays dead for non-admin users until the backend gives them a resource type or a parent permission (`getPermissionResourceType`). Test every migration of these with a non-admin reader.
4. **Not streamed at all:** payloads (`ResourceType.PAYLOAD`) and the `THREAT_ARSENAL` resource are excluded in `StreamService.RESOURCES_STREAM_EXCLUSION`, which confirms what the conventions say. A threat arsenal row is an injector contract plus its payload: contract events exist (under `injectorcontracts`), payload events do not. Making the arsenal live needs a backend decision first.
5. **No stream on standalone pages:** the player and observer pages (`public/components/channels`, `challenges`, `lessons`) and the admin challenge previews mounted in `Root.tsx` run without a layout, so without `useLiveStream`. Their stores (`channelreaders`, `simulationchallengesreaders`, `scenariochallengesreaders`) are synthetic DTOs no event writes. The `private/` side has no channel, challenge or lessons reader (only `Dashboard.tsx` and `TopBar.tsx`).
6. **Shared components crossing features:**
   - `TeamPopover` is used in the teams list, `TeamDetail`, `ContextualTeams`, `InjectTeamsList` and `QuickInject`.
   - `TeamPlayers` and `PlayerPopover` span the teams and players features.
   - `ContextualTeams` and `UpdateTeams` are only used by scenario and simulation.
   - `DocumentPopover` is used in documents, challenges, articles and inject documents.
   - `CreateTeam`, `CreateDocument` and `CreateChallenge` are used inline in pickers.
   - `CustomDashboardWrapper` is used by Home and the simulation and scenario analysis tabs.

   Teams, players and organizations are tightly coupled (membership lives on the team; the organization on the user): consider migrating them in sequence, `users` → `teams` → `organizations`, with `watch` on the owning type.
7. **Existing bugs the migration will expose or fix:**
   - Duplicate from the phishing landing page and email template lists does not add the copy (Redux write, local list).
   - Organization details shows its local copy, so a rename by someone else never shows.
   - `TeamDetail` and the channel, lessons and phishing details show a loader forever after a delete (`!entity` → `<Loader/>`).
   - `PersonDetail` and `OrganizationDetail` load **all** players and teams on mount.
   - `LessonsTemplates` still uses the old `PaginationComponent`.
8. **Possible dead code:** `admin/components/components/documents/Documents.jsx` (empty file), `ChannelsFilter.tsx` (no importer found), the `payloads` store key and schema (no `getPayload*` reader found).
9. **To check:**
   - Whether a membership-only change (`updateTeamPlayers`) emits a `teams` update event. Hibernate does not fire `@PostUpdate` for a collection-only change unless an owned column such as `team_updated_at` changes too.
   - Whether the stream payloads carry the computed DTO fields the screens show: `team_users_number` and the `team_*_expectations` scores on teams, `challenge_exercises` on challenges.
   - Whether `NotificationTrigger` events, which are `TenantBase` and not `UserScoped`, go to every user holding READ on `NOTIFICATION_TRIGGER` rather than only to their owner.
   - Whether `organizations` should stay in the reducer's `PLATFORM_ENTITIES`, since `Organization` is tenant-scoped.

### Notes

- **Counts (65 rows, "out of feature" rows excluded):** 🟢 0 · ✅ 9 (deployed injectors/collectors, injector detail, collector detail, executor screens and domains for admins only, connector instance status, group grant state "to check", the user's own `me` only with the users-read capability) · ⚠️ 23 (6 of them mixed) · ⛔ 16 · n/a 15 (write-only dialogs) · 2 other (autonomous defaults "to check", mitigations without screen).
- **Store key ≠ stream schema** (⛔ even where Redux is read): `marking_definitions` vs `markingdefinitions`; `catalog_connectors` vs `catalogconnectors` (and id `catalog_connector_id` vs `connector_id`); `injector_contracts` vs `injectorcontracts`; `tenantXtmHubRegistrations` vs `tenantxtmhubregistrations`; `tenantSettings` vs `settings` (reducer reroutes `settings` events to `platformParameters`).
- **Thunks writing to store keys nobody reads**: `platform_users`, `platform_groups`, `platform_roles`, `tenants`, `marking_definitions`. Stream writes to keys nobody reads: `tagrules`, `notifiers`, `customdomains`, `importmappers`, `connectorinstanceconfigurations`, `mitigations`.
- **Platform scope is never streamed**: `isVisibleForTenant` drops `DualScopeBase` rows with a null tenant, and every consumer has a tenant (default fallback). Platform groups, platform roles and platform settings cannot become live without a backend change. Users (plain `Base`) and tenants are streamed.
- **Admin-only streams**: entities without `getResourceType` (Executor, Domain, Mitigation, Tenant, CatalogConnector, ConnectorInstance) resolve to `UNKNOWN`, which `PermissionService` grants to admins/BYPASS only. Their readers are live for admins only.
- **Never streamed**: Vulnerability (explicit exclusion), ConnectorInstanceLog (exclusion), Grant, Token (no listener), SecretsProvider (not an entity), sessions.
- **The current user does not get its own `users` event** unless they hold the users-read capability: `me` (and so `rightsOf` in `root.tsx`) is then only refreshed by `useRefreshMe` (focus, 60 s throttle, refused write).
- **Entities whose change alters another user's rights**: group membership and group markings → `MarkingClearanceCacheManager.evictForUsers` → `clearance-changed` to the members → their TanStack queries `resetAll`; marking definition create / order change / delete → `evictAll` → every user; group roles, role capabilities, admin flag, grants → no stream signal to the members (only `useRefreshMe` → `AppQueryProvider` `invalidateAll`/`resetAll`). Platform group changes also evict clearance (`PlatformGroupService`).
- **Group grants "to check"**: `Group.grants` is `mappedBy = "group"`; add/remove only changes `grants` rows (no listener), so whether a `groups` update event fires depends on Hibernate treating the inverse collection as dirty. Verify with two browsers before relying on it.
- **Shared components**: `GroupPopover` (list + `GroupDetail`), `UserPopover`/`PlatformUserPopover` (list + `UserDetail`), `RolePopover` (list + `RoleDetail`), `OrganizationPopover` (settings list + `OrganizationDetail`); `ConnectorLayout`/`ConnectorPage`/`ConnectorPopover` serve injectors, collectors, executors and secrets providers through `ConnectorContext` — migrating one connector type touches the shared layout (split by entity, keep each read on one source).
- **Legacy `PaginationComponent` (V1)**: Tags, Attack patterns, XLS mappers — not V2, need the toolbar move.
- **DTO vs entity shapes**: injectors/collectors/executors store the `*Output` DTOs while the stream merges entity JSON (deep merge keeps DTO-only fields on updates, not on creates); a migration to queries removes this mix.
- **Global loaders**: `admin/Index.tsx` loads attack patterns, kill chain phases, tags and domains at login; `Organizations.tsx`, `OrganizationDetail.tsx`, `GroupDetail.tsx` add `fetchTags` / `fetchUsers`. Keep them while out-of-feature readers exist.
