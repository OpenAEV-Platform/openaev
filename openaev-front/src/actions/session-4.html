🧭 Introduction

L'OOP en TypeScript, avec ses interfaces, classes et ses composition, est très similaire à ce qu'on fait en java. Mais avec une syntaxe plus stricte et une couche supplémentaire : Spring, qui possède et fabrique les objets à votre place.

Les 4 piliers qu'on va parcourir aujourd'hui :

  • Héritage — partager un contrat et du code commun entre classes
  • Abstraction — masquer le "comment", exposer le "quoi"
  • Encapsulation — protéger l'état interne d'un objet
  • Polymorphisme — un même appel, un comportement différent selon l'objet réel

🧬 Héritage

Héritage — Mise en situation

Vous développez un logiciel qui pilote des distributeurs de billets (ATM) de plusieurs fabricants.

Questions :

  • Quelles opérations sont communes à tous les distributeurs, quel que soit le fabricant ?
  • Si vous écrivez une classe indépendante par fabricant sans rien partager, que se passe-t-il le jour où un nouveau fabricant arrive, ou qu'une règle commune change ?
  • Comment sépareriez-vous "ce que tout ATM sait faire" de "comment chacun le fait réellement" ?

Héritage — Réponses attendues

  • Retrait, consultation solde, éjection carte = un contrat commun à toutes les implémentations.
  • Sans partage : duplication de structure, et toute évolution du contrat commun oblige à modifier N classes indépendamment — risque d'incohérence.
  • On sépare via une classe (ou interface) commune qui définit le contrat ; chaque fabricant fournit sa propre implémentation en héritant de cette base.

Héritage — Rappel TypeScript

abstract class Atm {
  abstract withdraw(amount: number): void;
  abstract checkBalance(): number;
}
class DieboldAtm extends Atm { /* ... */ }
class NcrAtm extends Atm { /* ... */ }

En TS, le typage structurel (duck typing) rend l'héritage de classe moins central qu'en Java — souvent une simple interface suffit, sans hiérarchie de classes.

Héritage — Code réel OpenAEV

📁 openaev-api/.../executors/ExecutorContextService.java

public abstract class ExecutorContextService {

  public abstract void launchExecutorSubprocess(
      Inject inject, Endpoint assetEndpoint, Agent agent, String token)
      throws AgentException;

  public abstract List<Agent> launchBatchExecutorSubprocess(
      Inject inject, Set<Agent> agents,
      InjectStatus injectStatus, String token);
}

Étendue par plusieurs implémentations concrètes :

@Service(CrowdStrikeExecutorContextService.SERVICE_NAME)
public class CrowdStrikeExecutorContextService extends ExecutorContextService { ... }

@Service(PaloAltoCortexExecutorContextService.SERVICE_NAME)
public class PaloAltoCortexExecutorContextService extends ExecutorContextService { ... }

Point clé Java vs TS : extends est unique et obligatoire (héritage simple), et une classe abstraite peut porter du code partagé, pas juste des signatures — contrairement à une interface TS pure.

🎭 Abstraction

Abstraction — Masquer le "comment"

Vous conduisez une voiture avec un volant et des pédales, sans connaître les détails du moteur (thermique ou électrique) qui se trouve dessous.

L'abstraction, c'est montrer uniquement ce qu'il faut savoir pour utiliser un objet, jamais comment il est fabriqué en interne.

On réutilise directement l'exemple précédent : ExecutorContextService est l'abstraction.

// Le code appelant raisonne sur "un ExecutorContextService"
// sans jamais connaître la complexité de l'API CrowdStrike
// ou PaloAlto Cortex derrière launchBatchExecutorSubprocess(...)
executorContextService.launchBatchExecutorSubprocess(inject, agents, injectStatus, token);

🔒 Encapsulation

Encapsulation — Mise en situation

Un thermostat connecté : vous ne touchez jamais directement à la résistance ou au compresseur. Vous appuyez sur "+"/"-", et l'appareil refuse de descendre sous 5°C (hors gel) ou de dépasser 30°C, même si vous insistez.

Questions :

  • Pourquoi le fabricant ne vous laisse-t-il pas agir directement sur la résistance ?
  • Que se passerait-il si n'importe quel autre appareil de la maison pouvait modifier la température cible sans passer par ce bouton ?
  • Si demain le thermostat doit aussi enregistrer "dernière modification par qui/quand", où cette règle doit-elle vivre ?

Encapsulation — Réponses attendues

  • Protéger des invariants (sécurité/physique) via un point de passage unique.
  • Un bug ailleurs dans la maison pourrait violer une règle métier critique sans que le thermostat "s'en rende compte" — perte de contrôle de l'état.
  • La règle doit vivre dans l'objet qui possède l'état, pas dupliquée chez chaque appelant.

Encapsulation — Rappel TypeScript

class Thermostat {
  #target = 20;

  setTarget(v: number) {
    if (v < 5 || v > 30) throw new Error("out of safe range");
    this.#target = v;
  }
}

Le champ privé #target ne peut être modifié que via setTarget, qui impose la règle métier.

Encapsulation — Code réel OpenAEV (1/2)

📁 openaev-model/.../database/model/Inject.java

// UpdatedAt now used to sync with linked object
public void setStatus(InjectStatus status) {
    this.updatedAt = now();
    this.status = status;
}

Même pattern répété pour setDependsOn, setTags, setTeams, setAssets, setAssetGroups.

Encapsulation — Code réel OpenAEV (2/2)

Méthode clean() — remise à zéro cohérente :

@JsonIgnore
public void clean() {
    this.setStatus(null);
    this.communications.clear();
    this.expectations.clear();
    this.findings.clear();
    this.setCollectExecutionStatus(COLLECTING);
}

Bonus — 📁 InjectStatus.java :

public void addErrorTrace(String message, ExecutionTraceAction action) {
    ExecutionTrace newTrace = new ExecutionTrace(
        this, ExecutionTraceStatus.ERROR, List.of(), message, action, null, null);
    this.getTraces().add(newTrace);
}

La liste traces n'est jamais manipulée directement (.add()) depuis l'extérieur — on passe toujours par addTrace/addErrorTrace/addInfoTrace/addWarningTrace.

🎭 Polymorphisme

Polymorphisme — Mise en situation

Une télécommande universelle : le bouton "Power" est toujours au même endroit et se presse pareil, quel que soit l'appareil branché (TV Samsung, LG, Sony).

Questions :

  • Que doit "savoir" la télécommande sur l'appareil en face d'elle pour fonctionner ?
  • Si un nouveau modèle de TV sort demain, faut-il modifier la télécommande ?
  • Qui décide, et à quel moment, du comportement réel qui s'exécute derrière le bouton Power ?

Polymorphisme — Réponses attendues

  • Elle n'a besoin de connaître que le contrat (Power/Volume/Chaîne), jamais les détails internes de chaque TV.
  • Non : chaque nouvelle TV s'adapte au même protocole, seul le comportement change, pas l'interface.
  • La décision est prise à l'exécution (runtime), pas à l'écriture du code de la télécommande — c'est le dynamic dispatch.

Polymorphisme — Mise en situation

Vous réservez une course sur une application de VTC. Vous appuyez toujours sur le même bouton "Réserver une course". Mais le chauffeur qui accepte réellement la course — et donc la voiture, l'itinéraire, le style de conduite — est différent à chaque fois, et vous ne le savez qu'au moment où quelqu'un accepte.

Questions :

  • Quand vous appuyez sur "Réserver", que savez-vous à l'avance du chauffeur qui va réellement prendre en charge la course ?
  • Qui décide quel chauffeur va traiter votre demande, et à quel moment cette décision est-elle prise ?
  • Si demain un nouveau chauffeur s'inscrit sur la plateforme, faut-il changer votre application ou votre façon de réserver ?

Polymorphisme — Réponses attendues

  • Rien : vous connaissez seulement le contrat ("réserver une course"), jamais l'identité ni les caractéristiques du chauffeur réel avant l'affectation.
  • La plateforme (l'algorithme de dispatch) décide, au moment de la demande — à l'exécution, pas à l'écriture du code de votre appli.
  • Non : le protocole de réservation reste identique, seul le chauffeur affecté change — sans jamais toucher à l'appli existante.

Polymorphisme — Rappel TypeScript

interface Remote { power(): void; }
class SamsungTv implements Remote { power() { /* ... */ } }
class LgTv implements Remote { power() { /* ... */ } }

function pressPower(tv: Remote) {
  tv.power(); // ne sait pas laquelle
}

Polymorphisme — Le mécanisme technique

Deux formes existent, souvent confondues. On ne s'intéresse ici qu'à la seconde :

Surcharge (overloading)Redéfinition (overriding)
RésolutionÀ la compilation (signature)À l'exécution (type réel de l'objet)
Aussi appelé"Static polymorphism""Dynamic polymorphism" / dynamic dispatch
Exempleprocess(String s) vs process(int i)CrowdStrikeExecutorContextService override de launchBatchExecutorSubprocess
C'est notre sujet ?❌ Non✅ Oui

Le vrai mécanisme du polymorphisme "orienté objet" repose sur une distinction fondamentale :

  • Type déclaré (compile-time) — ce que le compilateur voit dans la variable
  • Type réel (runtime) — l'objet effectivement présent en mémoire

Le compilateur vérifie seulement que le type déclaré possède la méthode. La JVM choisit quelle implémentation exécuter en regardant le type réel, à chaque appel — c'est le dynamic dispatch.

Polymorphisme — Le mécanisme, dans notre code

ExecutorContextService executorContextService =
    manager.request(new ComponentRequest(executor.getName()), ExecutorContextService.class);
//  ↑ Type DÉCLARÉ (compile-time) : ExecutorContextService
//    Le compilateur autorise l'appel car ExecutorContextService définit la méthode.

executorContextService.launchBatchExecutorSubprocess(inject, agents, injectStatus, token);
//  ↑ Type RÉEL (runtime) : CrowdStrikeExecutorContextService, PaloAltoCortexExecutorContextService...
//    La JVM regarde l'objet EFFECTIF en mémoire pour choisir QUELLE implémentation exécuter.

C'est exactement le point de la mise en situation VTC :

  • Le type déclaré = le bouton "Réserver une course" (le contrat, toujours identique)
  • Le type réel = le chauffeur effectivement assigné (connu seulement à l'exécution)

💡 En Java, l'annotation @Override ne déclenche pas le dynamic dispatch — le compilateur vérifie juste que vous redéfinissez bien une méthode existante de la classe parente. Le dispatch dynamique, lui, se produit toujours pour les méthodes non-static/non-private/non-final, avec ou sans l'annotation.

Polymorphisme — Spécificités Spring

  • @Service(CrowdStrikeExecutorContextService.SERVICE_NAME) : chaque implémentation s'enregistre comme bean Spring sous un nom métier.
  • Spring maintient ces beans en mémoire ; c'est le code appelant qui va chercher le bon bean par son nom à l'exécution — aucun new CrowdStrikeExecutorContextService() dans ExecutionExecutorService. C'est l'inversion de contrôle.
  • @Qualifier/@Primary : mécanisme plus simple, pour choisir entre 2-3 beans candidats à l'injection directe (pas de lookup dynamique par nom).

⚠️ Piège fréquent : les proxies AOP. Un bean annoté @Transactional/@Async est souvent un proxy dynamique (CGLIB/JDK) qui intercepte l'appel — encore du polymorphisme, mais fabriqué par le framework. Un appel interne (self-invocation, this.methodeAnnotée()) ne passe pas par le proxy et perd le comportement transactionnel/async.

🧱 SOLID

SOLID — Les 5 principes

LettrePrincipeEn une phrase
SSingle ResponsibilityUne classe = une seule raison de changer
OOpen/ClosedOuvert à l'extension, fermé à la modification
LLiskov SubstitutionUne sous-classe doit pouvoir remplacer sa classe parente sans rien casser
IInterface SegregationPréférer plusieurs interfaces spécifiques à une seule interface fourre-tout
DDependency InversionDépendre d'abstractions, pas d'implémentations concrètes

SOLID — Exemple concret OpenAEV

Reprise du même fil (ExecutorContextService) pour 2 lettres :

  • Open/Closed : ajouter un 6ᵉ exécuteur (ex: un futur "Qualys") ne nécessite aucune modification de ExecutionExecutorService ni des implémentations existantes — il suffit d'ajouter une nouvelle classe @Service qui étend ExecutorContextService.
  • Dependency Inversion : ExecutionExecutorService dépend du type abstrait ExecutorContextService, jamais de CrowdStrikeExecutorContextService ou PaloAltoCortexExecutorContextService directement.
// La signature ne mentionne jamais une implémentation concrète
ExecutorContextService executorContextService =
    manager.request(new ComponentRequest(executor.getName()), ExecutorContextService.class);
